# AI コンテキストガイド & 開発憲章

このドキュメントでは、**scripture-habit** プロジェクトのコアアーキテクチャ、制約事項、状態のコンベンション、およびコーディングパターンについて定義します。このリポジトリでコードを生成または変更する際は、以下のルールに従ってください。

---

## アーキテクチャの基礎

クロスプラットフォーム（WebおよびAndroid）で優れたパフォーマンスを発揮できるように設計された、クリーンでタイプセーフ、かつモジュール化されたアーキテクチャを採用しています。

### 1. ロジックとコンポーネントの分離
*   **UIコンポーネント**: レンダリング、レイアウト、およびスタイリング*のみ*を担当します。UIコンポーネント内に、直接のAPI呼び出し、ルーティング、または複雑な状態計算を記述してはいけません。
*   **カスタムフック / サービス**: すべてのデータ同期、API呼び出し、ロジック計算、およびビジネスルールは、フック（フロントエンド）またはサービス（バックエンド）内に記述する必要があります。
*   **スタイリング**: グローバル変数（`src/index.css`）とグラスモーフィズム（ガラス風UI）用のユーティリティクラス（例: `.AppGlass`）を適用した **Vanilla CSS** を使用します。
    *   *制約*: 明示的に要求されない限り、**TailwindCSSやユーティリティライブラリは使用しないでください**。CSSはモジュール化され、読みやすい状態を維持してください。

### 2. 状態管理（Source of Truth の原則）
パフォーマンスの問題やデータの同期エラーを防ぐため、状態は常にその一次ソース（発生源）に基づいて分類し、適切なツールを使用してください。

| ステートの種類 | 管理ツール | ガイドライン |
| :--- | :--- | :--- |
| **サーバーのメタデータ** | **TanStack Query (React Query)** | 標準的なステートレスのAPIリクエスト（設定、プロファイル、静的メタデータの取得など）に使用します。 |
| **リアルタイムのソーシャル状態** | **Firebase client SDK `onSnapshot`** | チャットメッセージ、既読マーカー、グループ統計、およびアクティブな参加者状態に使用します。 |
| **グローバルなUI状態** | **Zustand** | クライアント専用の状態（モーダル、ダークモードの切り替え、ナビゲーション状態など）に使用します。 |
| **ユーザーアイデンティティ** | **React AuthContext** | 現在のユーザーのセッションとアイデンティティを共有するために使用します。 |

## 書き込みポリシーとデータの整合性

本番環境のセキュリティとオフラインでの応答性（Firestore Offline Persistence）のバランスを取るため、アプリケーションは**ハイブリッドな書き込みポリシー**を採用しています。

### 1. Firestoreルールとフロントエンドの制限
*   **共同作業用リソース (`messages`、`members`、`cheers`、`groups`)**:
    改ざんや整合性の破綻を防ぐため、これら共同作業用リソースは `firestore.rules` において `allow write: if false;`（`groups` は `create` も制限）に設定されています。これらに対して、フロントエンドのコードから直接書き込みを呼び出しては**いけません**。
*   **個人用リソース (`users`、`private/tokens` captains/groupStates`、`letters`)**:
    オフライン時のデータ永続化と即時反映を可能にするため、認証された本人（`request.auth.uid == userId`）からの直接の作成・更新がルールによって安全に許可されています。
*   **フロントエンドの例外**:
    通報（`reports`）の作成はフロントエンドから直接行えます。※以前許可されていた直接のグループ作成（`groups` の `create`）は、セキュリティとデータ一貫性を担保するため廃止され、現在はバックエンドAPI（`/api/groups/create-group`）経由に一本化されています。

### 2. バックエンド優先（APIミューテーション）
*   共有リソースの状態の更新（グループの作成、ノートの投稿、応援（チア）、グループへの参加、管理者権限の譲渡など）は、**Vercel Functions**（`api_internal/routes/*`）を介してExpressバックエンドを経由する必要があります。
*   **アトミックトランザクション（Read-before-Writeの強制化）**:
    複数のレコードに影響を与えるすべての更新は、失敗時にロールバックされることを保証するために、`runPhasedTransaction()` でラップする必要があります。
    *   *制限と移行ロードマップ*: トランザクション内の「読み込み（Read）の後に書き込み（Write）を実行する」というFirestore Adminの制約を遵守させるため、生の `db.runTransaction()` の直接使用はESLintルール（`no-restricted-properties`）により制限（警告）されています。新規実装は必ず `runPhasedTransaction()` を使用してください。歴史的な残存トランザクション（`auth.ts`）の移行がすべて完了し次第、警告（warn）からエラー（error）へ引き上げられます。
    *   *型レベルの防御*: `runPhasedTransaction` の `read` フェーズ callback が受け取る引数は `ReadOnlyTransaction` 型（`get` と `getAll` のみが許容される型）に制限されているため、読み込みフェーズで誤って書き込みメソッド（`set`, `update`, `delete`）を実行することはコンパイルエラーとして100%遮断されます。
    *   *冪等性の保証（副作用の禁止）*: Firestore トランザクションは競合発生時に自動で複数回リトライされます。そのため、トランザクションブロック（特に `write` フェーズ）の中には**「データベースの冪等（Idempotent）な更新処理」のみを記述してください。** 外部API呼び出し、Discord/Slack等のメッセージ通知送信、非アトミックなID生成といった「副作用を伴う処理」は、トランザクションが正常にコミットされた後（トランザクションブロックの外）で実行してください。

### 3. 統一された Express エラーハンドリング
*   Express のルートハンドラ内で発生したビジネスロジックエラー（権限不足、リソースなし、入力値エラーなど）は、汎用の `Error` ではなく [api_internal/lib/errors.ts](file:///c:/Users/dazhi/code/final-project/scripture-habit/api_internal/lib/errors.ts) で定義されている `AppError` のサブクラス（`ForbiddenError`、`NotFoundError`、`ValidationError`）をスローしてください。
*   `catch` ブロックでは個別にステータスコードを返さず、必ず `sendErrorResponse(res, error, 'Fallback message')` ヘルパーを使用してください。これにより、エラークラスに応じた正しい HTTP ステータスコード（403, 404, 400 等）とエラーコードが型安全にクライアントへ返却されます。

### 4. Firestore TTL とデータサイズ上限
*   データベース操作を効率的に保ち、チャットのパフォーマンスをスケールさせるため、チャットメッセージは Firestore のネイティブ機能である Time-to-Live (TTL) 機能（`expireAt` フィールド）を使用して、30日後に自動的に削除されます。
*   アクティブなチャット同期は最新の25件のみをロードするように最適化されており、クライアントを軽量に保ち、過剰な読み取り操作を防ぎます。

## AI とローカライズの統合

### 1. 多言語設計
*   アプリケーションは多言語をサポートしています。UIに文字列をハードコードしないでください。
*   フロントエンドでは常に `t()` 翻訳フック（`useLanguage` から取得）を使用し、バックエンドではロケールバンドル（`api_internal/locales/` 下）を使用してください。

### 2. Geminiプロンプトとペルソナ
*   応答速度を最大化するため、グローバルで `thinkingLevel: "minimal"` を指定した **Gemini 3.1 Flash-Lite Preview** を使用します。
*   プロンプトは常に**「心強いファシリテーター (Encouraging Facilitator)」**のペルソナ（温かく、親しみやすく、個人的な応用に焦点を当て、学術的または神学的な専門用語を避けるスタイル）を実装する必要があります。

## テストと信頼性

*   **セキュリティルール**: `api_internal/rules.test.ts` 内で `@firebase/rules-unit-testing` を使用して、セキュリティルールの調整内容を検証します。
*   **API連携**: エミュレートされたFirestoreサービスに対してExpressルートをテストします。ユーザーコンテキストのために `verifyIdToken` が適切にモックされていることを確認してください。
*   **プロンプト回帰テスト**: 言い回しの変更によって構造化モデルの動作が損なわれるのを防ぐため、Geminiプロンプトの記述（`ai_integration.test.ts`）は常にスナップショットテストを行ってください。
